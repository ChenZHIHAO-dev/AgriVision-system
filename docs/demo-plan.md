# AgriVision 植保问诊 Demo 实施规划

本项目服务河南南阳及周边中原地区的农资企业，优先小麦，再扩展玉米、花生。用户拍照后获得疑似问题、需要补充的信息、防治措施和适用产品，并能在同一问诊中继续交流。首版在用户电脑上运行，后续使用 AutoDL 扩大训练。

规划日期为 2026 年 11 月 17 日。下文的类别、训练规模和验收目标属于实施建议；公开来源中的季节性预报用于规划优先级，不代表当前田间发生情况。

## 南阳的首批病虫害范围

南阳市农业农村局发布的 2026 年小麦防控信息涉及赤霉病、条锈病、白粉病、纹枯病、茎基腐病和麦蚜。[南阳小麦防控信息，2026 年 4 月 2 日](https://nyj.nanyang.gov.cn/2026/04-02/1394937.html)

南阳的玉米资料特别关注南方锈病；当地及河南相关农技资料还涉及大小斑病、弯孢叶斑病和玉米螟等。花生资料涉及叶斑病、白绢病、根茎部病害和食叶、地下害虫。[南阳玉米南方锈病防控](https://www.nanyang.gov.cn/2024/07-31/540909.html)、[河南秋作物防控指导，2026 年](https://zzny.zhengzhou.gov.cn/nysc/10164772.jhtml)、[全国花生病虫害防控方案，2025 年](https://www.agri.cn/sc/nszd/202502/t20250228_8758866.htm)

| 作物 | 应进入知识与咨询范围的问题 | 图像识别安排 |
| --- | --- | --- |
| 小麦 | 条锈病、白粉病、赤霉病、纹枯病、茎基腐病、麦蚜；叶锈病作为易混淆类别补充 | 首批处理叶片；赤霉病需麦穗照片，根茎病害需茎基部照片和补问 |
| 玉米 | 南方锈病、大斑病、小斑病、弯孢叶斑病；玉米螟、草地贪夜蛾、黏虫等 | 叶部病害随后接入；虫害需要虫体及取食痕迹近照 |
| 花生 | 叶斑病、网斑病、锈病、白绢病、根腐病、茎腐病；蚜虫、叶螨、棉铃虫、斜纹夜蛾、蛴螬等 | 先叶斑病类、锈病；死棵和地下害虫走针对性补拍与复核流程 |

这份清单结合区域资料与业务需求制定，不按发生率排名。具体药剂适用性继续核对产品登记和标签。

## 图像模型的上线顺序

| 批次 | 目标类别 | 接入条件 |
| --- | --- | --- |
| 第一批 | 小麦条锈病、叶锈病、白粉病、未见已支持病害明显特征，共 4 类 | 数据许可、标签复核、独立测试与拒识流程通过 |
| 第二批 | 玉米大斑病、小斑病、普通锈病、南方锈病、未见已支持病害明显特征，目标 5 类 | 每类独立验收，普通锈病与南方锈病分别标注；南方锈病样本不足时保留待复核状态 |
| 第二批 | 花生叶斑病类、锈病、未见已支持病害明显特征，目标 3 类 | 初期合并早晚叶斑病；只有取得可靠细分类标签后才拆分 |
| 后续 | 小麦赤霉病、虫害检测、根茎病害辅助识别 | 为麦穗、虫体、根茎分别补足数据、采集规范和评测集 |

以上共 12 个分作物目标类别，不含后续扩展。模糊、非目标作物、未支持病害和信息不足属于系统状态，需单独验证拒识表现。分类模型的健康类别不代表整株或整块田无病。

第一批交付时，三个作物均有资料咨询入口；只有已通过验收的类别显示为“支持图片识别”。其他问题保存为咨询记录并引导补拍或联系农技人员，避免展示虚构的识别结果。

## 一次问诊的处理流程

1. 用户选择作物、确认地区并拍照或上传。先接收一张主要症状近照，允许继续补充叶背、整株或田间照片。
2. 后端检查图片格式、大小、清晰度和支持范围，保存问诊记录，再调用该作物的视觉模型。
3. 返回候选类别和不确定状态。需要信息时补问生育期、症状出现时间、分布、近期降雨及用药。
4. 按作物、部位、地区、生育期和疑似问题检索资料，给出检查项与防治措施。
5. 产品匹配规则查询已维护的登记与标签资料；满足适用条件时提供用药方案卡片。
6. 展示公司目录中符合条件的产品。没有匹配产品时，仍保留有依据的防治说明。
7. 用户在同一问诊内追问、补图或反馈变化。补图产生新的识别版本，并保留原记录。

地区、季节和天气用于调整补问与资料检索，不能单独确定病害。首版天气由用户描述；接入天气服务后展示地点和更新时间。

## 对话如何组成

每个问诊有独立的图片、作物、地区、模型结果、资料来源和消息历史。DeepSeek 接收这些信息及当前问题，不把不同问诊的上下文混在一起。

| 情况 | 对话任务 | 输出方式 |
| --- | --- | --- |
| 图片清楚且候选明确 | 解释疑似问题，补齐决定处理方案的条件 | 简短结论、下一步、防治依据 |
| 候选相近 | 询问最有区分度的症状，引导补拍相应部位 | 每轮优先 1 至 2 个问题，提供可点选答案 |
| 用户只描述黄叶、死棵 | 询问作物、生育期、根茎状态、积水、近期施药等 | 保留多个可能原因，给出观察与复核路径 |
| 用户询问用药 | 核对具体产品、含量剂型、作物对象、生育期和近期施药 | 有适用依据的方案卡片及说明 |
| 用户补图复查 | 比较用户描述和新照片，更新候选与建议 | 显示本次变化，保留历史依据 |

示例补问：“这是整块田普遍发黄，还是零星几株？”“方便补一张叶背近照吗？”“近期用过什么药、什么时候用的？”问题根据当前问诊动态选择。

DeepSeek 模型标识通过后端配置读取；截至规划日期，官方文档提供 `deepseek-flash` 等模型。密钥只保存在后端环境配置中。[DeepSeek 官方模型文档](https://api-docs.deepseek.com/quick_start/pricing/)

## 用药方案与公司产品

用户所需的“药物配方”在产品中表达为可核对的用药方案：具体制剂、适用对象、标签用量、施用方式、施药条件、最多次数和相关间隔要求。规则从产品资料生成结构化卡片，DeepSeek 解释卡片并进行补问。

农药使用应遵循标签规定的范围、方法、剂量和技术要求。因此产品匹配需要保留登记证号、有效成分及含量、剂型、适用作物和对象、标签原文、核对日期等信息。[农业农村部《农药管理条例》第三十四条](https://fgs.moa.gov.cn/flfg/202312/t20231205_6442161.htm)

单个成分的资料不能直接替代不同含量、不同剂型商品的标签。首版优先展示有完整依据的单个登记制剂及登记复配制剂。多产品混配只接入有明确适用依据、经农技人员维护的方案模板，匹配时逐项检查适用条件。

| 资料对象 | 必要信息 |
| --- | --- |
| 产品 | 登记信息、产品名称、成分含量、剂型、作物、防治对象、用量及单位、施用方式、标签依据、更新日期 |
| 方案 | 产品及标签版本、适用生育期、施药条件、次数与间隔、禁忌、维护人和有效状态 |
| 公司目录 | 公司商品标识、包装规格、对应登记产品、可售状态和联系渠道 |
| 问诊结果 | 触发规则、采用的方案版本、缺失信息、引用资料和后续反馈 |

每个剂量必须保留单位和依据。按亩制剂量与稀释倍数分别处理；后续的药桶或面积换算由确定的单位计算执行，缺少必要参数时先补问。演示产品明确标注示例，不编造真实登记号、标签或药剂数值。

## 首版 RAG 知识库

资料分为区域病虫情报、病害识别与鉴别、综合防治、产品标签、公司方案五类。每条保留来源、发布日期、地区、作物、器官、适用阶段及资料维护状态。

先整理约 30 至 60 条经核对的知识卡。检索先按作物和问题过滤，再做中文关键词与语义检索；产品剂量与适用关系由结构化规则读取。旧季节预报保留年份，不当作实时虫情。用户上传和检索资料作为数据处理，不执行其中的指令。

结果先显示结论和下一步，再按需展开来源。RAG 增补农业知识；后续微调主要用于稳定问答风格或改善视觉识别，新增和变化的标签资料继续维护在知识库中。

## 本机训练与后续 AutoDL

本机已检测到 RTX 3060 Laptop 6GB 显存、约 32GB 内存和 Ryzen 9 5900HX。先建立独立 Python 环境，核对 PyTorch 与驱动兼容性，再训练和推理。

| 项目 | 首轮安排 |
| --- | --- |
| 主模型候选 | EfficientNet-B0，预训练权重迁移学习 |
| 轻量对照 | MobileNetV3-Small，用同一数据划分比较效果和速度 |
| 初始输入 | 224 像素试跑；细小症状再比较更高分辨率 |
| 初始批量 | 8 至 16，结合混合精度与实际显存调整 |
| 训练过程 | 先训练分类头，再逐步解冻；只对训练集在线增强 |
| 模型选择 | 验证集 Macro-F1、各类召回率、混淆矩阵、拒识表现和实拍评测 |
| 推理记录 | 模型版本、标签映射、预处理、分数、耗时和拒识原因 |

两种候选均有成熟的卷积网络实现。[EfficientNet 论文](https://arxiv.org/abs/1905.11946)、[MobileNetV3 论文](https://arxiv.org/abs/1905.02244)

首轮重点把数据与流程跑通；扩充数据后再决定是否增加模型规模。AutoDL 继续运行相同的配置、数据清单、划分和评测脚本。使用相对路径，保存数据与权重校验值，导出模型时同时保存标签、预处理和评测报告。训练租卡与日常演示服务分开安排。[AutoDL 帮助文档](https://www.autodl.com/docs/)

## 软件与网络结构

前端采用 uni-app、Vue 3 与 TypeScript，分别构建网页和微信小程序；共用数据模型、请求与业务流程，分端处理拍照、上传、布局和对话更新。后端采用 FastAPI，病例、推理、检索、产品规则和 DeepSeek 适配先集中在一个服务内。[uni-app 跨端文档](https://uniapp.dcloud.net.cn/tutorial/platform.html)

本地先使用 SQLite 保存结构化记录，文件目录保存上传图片；训练数据、权重和用户记录独立存储。图库、模型和 DeepSeek 失败分别反馈，已得到的识别结果不会因对话失败而丢失。

电脑网页先访问本机服务，微信小程序先在开发者工具中联调。手机的 localhost 指向手机自身；真机访问需要手机可达的测试地址，并按微信当时的网络与域名要求配置。对外部署另行安排，避免把开发调试设置当作发布环境。

## 实施顺序与验收

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 一 | 移动端与桌面端的关键页面原型、组件和页面状态 | 新用户能找到拍照、理解结果、补充信息和找回记录 |
| 二 | 数据清单、标签映射、去重与分组划分、第一批训练基线 | 清楚记录有效原始图数量，训练与评测无已知重复泄漏 |
| 三 | 两端上传、真实小麦模型推理、病例与历史记录 | 用户图片走真实权重，低质量和不支持对象有对应反馈 |
| 四 | DeepSeek、首批知识卡、产品方案规则 | 回答绑定当前问诊，引用可查，产品与剂量字段可追溯 |
| 五 | 玉米和花生模型按类接入、双端真机联调、GitHub 交付 | 界面支持范围与模型一致，代码和说明可在本机复现 |

模型验收分别报告内部测试与独立实拍表现，不将公开数据集分数作为南阳田间效果。业务验收包含模糊图、非目标图片、相似病害、混合症状、资料不足、无适用产品和 API 超时等情况。性能先测单用户识别与完整问诊耗时，再确定可承诺的等待时间。

首个可用 Demo 的核心验收是：拍一张支持范围内的小麦照片，得到真实模型候选，看到有依据的建议，并能继续围绕该照片追问。首版先完成这个流程，再扩充类别和业务模块。
